# Configuration decisions and their limits

These settings support the current small local lab. A number in configuration is not a measured capacity or reliability claim. See the [quality scenarios](../requirements/QUALITY_SCENARIOS.md) and [decision log](../DECISION_LOG.md).

| Setting / responsibility | Why this value/mechanism; alternative | Trade-off and failure behavior | How to prove / revisit |
|---|---|---|---|
| Java host bind `127.0.0.1` | Keep the unauthenticated demo local; `0.0.0.0` would expose a shared buyer | Containers override it only on the private Compose network; the gateway publishes loopback8090 | Inspect Compose bindings; add identity/object authorization before untrusted exposure |
| PostgreSQL17.6, own volume | Match integration and runtime locking/constraint semantics; H2 or Ark's database would obscure the learning boundary | One database supports ACID but is a shared failure domain; volume retention is not backup | Fresh Testcontainers migrations, restart/persistence check; see ADR003/008 |
| Hikari maximum12 | Bound DB concurrency while allowing the eight-request race plus small operational headroom; default10 is a plausible alternative | Not tuned for throughput. More connections are not automatically faster; saturated callers wait/fail | Phase2 must measure contention/CPU/DB. The race tests exercise concurrent connections, not a pool-sizing benchmark |
| Connection acquisition5s / transaction10s | Avoid unbounded waiting for a pool slot or local SQL work; infinite waits hide failure | These limits are distinct, not an end-to-end SLO; PostgreSQL statement/lock behavior still matters | Data-access errors map to503; inspect rollback/retry tests and add controlled lock/pool drills before stronger reliability claims |
| PostgreSQL READ COMMITTED | A fresh statement snapshot after a competing key claim sees its committed winner | Repeatable-read/serializable need different serialization-failure handling | Eight-way same-key integration test; do not silently change DB isolation |
| Flyway startup migrations | Refuse to run against an unknown schema; manual DDL is harder to reproduce | A bad migration blocks startup. Existing applied files stay immutable; V3 adds an explicit terminal-payment guard | All migrations run on fresh PostgreSQL in every integration suite; preserve evidence when a migration fails |
| Strict unknown JSON properties / quantity1–10 | Reject client price fields and bound the first checkout model; accepting arbitrary properties can conceal contract drift | Future additive input fields require a contract/version decision; this is deliberately a single-product exercise | Invalid-price/quantity HTTP tests and structural OpenAPI guards |
| JSON console logging / health+info only | Useful machine-readable startup/error evidence without choosing a logging platform or exposing environment details | No complete RED dashboard, distributed trace or alerting is implemented | Startup logs and Compose health checks; Phase6 adds monitoring from actual operational questions |
| Nginx proxy timeout15s, browser abort15s | Bound local waiting; an unlimited timeout can leave an unusable UI | Similar deadlines can race, and pool/transaction/network time do not form an exact global budget. A timeout does not prove rollback | Browser preserves exact pending request; live committed-response-loss test proves safe replay |
| `proxy_next_upstream off` | Avoid hidden POST retries by infrastructure; a proxy retry policy is an alternative only with explicit semantics | Client controls the visible exact-key retry. No automatic resilience/circuit-breaker capability is claimed | Read gateway config; real browser response-loss/replay scenario |
| Same-origin gateway / Vite proxy | No current need for permissive CORS; separate public frontend/API origins add policy and credential complexity | The demo still lacks authentication/CSRF session architecture; loopback containment is the current limit | Browser/API integration tests; ADR013 is explicitly deferred |
| CSP, nosniff, framing denied | Static assets need only same-origin script/style/connect and CSS illustrations | Headers reduce browser attack surface; they do not establish secure user isolation | E2E against the production gateway verifies assets/functionality under the policy; no broad security certification |
| Health readiness and `make up --wait` | Start web only after DB and API health; starting by process existence alone can serve failures | Failure blocks startup rather than falsely reporting readiness. Polling intervals/timeouts are local startup budgets | Actual full-image build/startup and healthy db/api/web checks |
| Exact npm lock / pinned runtime dependencies | Reproducible package graph and a tested compatibility set; floating latest makes diagnosis harder | Patches still need review, tests and periodic maintenance | `npm ci`, strict TypeScript build, component tests and live E2E |
| Optional BuildKit proxy/CA secrets | Support restricted/corporate networks without baking private setup into source/images | Cloud setup can fail when proxy DNS or CA changes; never disable TLS to make it pass | The images built with verified CA/proxy routing; refresh environment-specific overrides outside source |
| CI scoped to `ecal/**` | Exercise this independent project without changing the Ark reactor | Hosted CI is not asserted from local evidence; security/license scans remain Phase6 work | The same make targets were exercised locally; inspect future hosted job results separately |

The safe interview answer is conditional: “These defaults bound the current local exercise. I would measure the actual workload and failure behavior before claiming the pool size, timeout budget, SLO or deployment is appropriate for a customer.”

## Phase 2 fixed bounds

CSV file 256 KiB; multipart request 300 KiB; 1000 rows; batches 50; four workers; queue sixteen; one in-flight file per JVM. Import worker transactions use a ten-second timeout. Nginx exact import route and browser use 120-second read/request timeouts; ordinary requests keep fifteen seconds. Hikari stays at twelve connections. These bounds are deliberate fixed lab choices, not undocumented environment variables or measured production sizing.

## Phase 3 mode

`compose.phase3.yaml` uses separate credentials/volumes and publishes only loopback 8091. `ECAL_PHASE3_ORDERS_PASSWORD`, `ECAL_PHASE3_INVENTORY_PASSWORD`, `ECAL_PHASE3_PAYMENT_PASSWORD` are optional private Compose settings; changing environment values does not rotate a retained PostgreSQL role password. Defaults are isolated synthetic-lab values. Each service reads only its ECAL_DB_URL/USER/PASSWORD. Orders additionally reads ECAL_INVENTORY_URL, ECAL_PAYMENT_URL and finite ECAL_REMOTE_CONNECT_MS/REQUEST_MS (500/2000 default; validated ranges 50–2000/100–5000). Lease duration is fixed at 30 seconds; writes match its token. Health checks cover the node's database, not global workflow availability.

Module-specific configuration files are inventory-application.yaml, payment-application.yaml and orders-application.yaml. Each main sets its own config name. Full Docker uses service port 8080 internally. Host IDE defaults: Orders 8092/database 5545, Inventory 8093/5546, Payment 8094/5547. The dev Compose override publishes only the database loopback ports. Vite uses `VITE_ECAL_MODE=distributed` at build/dev time and `ECAL_API_TARGET=http://127.0.0.1:8092` for the dev proxy. Do not run Docker app mode and IDE services against the same working dataset concurrently.

## Phase 4

`compose.phase4.yaml` uses isolated project `ecal-phase4`, browser loopback port **8095**, four independent owner databases and one persistent Kafka 3.9.1 broker. `ECAL_EVENTS_ENABLED=true` enables the conditional platform and worker. `ECAL_KAFKA_BOOTSTRAP=kafka:9092` is internal; only the optional `compose.phase4.dev.yaml` exposes Kafka loopback 9094 and database ports 5555–5558.

Operational owners set `ECAL_FLYWAY_LOCATIONS=classpath:db/<owner>,classpath:db/events,classpath:db/events-<owner>`. Reporting includes its own locations by default. Never enable event workers without these migrations. Phase 3 leaves events false and uses only its V1 location. Database password overrides are `ECAL_PHASE4_ORDERS_PASSWORD`, `ECAL_PHASE4_INVENTORY_PASSWORD`, `ECAL_PHASE4_PAYMENT_PASSWORD`, `ECAL_PHASE4_REPORTING_PASSWORD`; defaults are local development values.

`VITE_ECAL_MODE=events` selects acceptance/polling and reporting. For IDE development, `ECAL_API_TARGET` selects Orders and `ECAL_REPORTING_TARGET` selects Reporting. JVM defaults remain 8092/8093/8094; Reporting defaults to 8096. `ecal.relay-delay-ms` defaults to 100, `ecal.saga-delay-ms` to 500; `ecal.worker-initial-delay-ms` defaults to 1000 and exists so integration tests can control exact crash boundaries. See the [Phase 4 guide](../learning/PHASE-04.md).

Optional `compose.phase4.compact.yaml` replaces the four PostgreSQL instances with four databases and ordinary roles in one instance; bootstrap credentials are given only to that container via `ECAL_PHASE4_BOOTSTRAP_PASSWORD` (local default `bootstrap_dev_only`). A separate `compact-data` volume keeps its dataset distinct from the default topology. Use the same two Compose files for start/stop; do not combine the compact and IDE dev overrides.
